# Технический конспект privacyvpn — как работает каждая фича

Цель: понять «на пальцах» сеть + бэкенд за каждым нашим обещанием.
Формат каждого пункта: **Что обещаем → Как работает → Как у нас в коде → Подвох/честность.**

---

## 0. Минимальный ликбез (прочитать первым)

- **Пакет** — порция данных в сети. На «конверте» написан адрес отправителя и получателя (IP).
- **IP-адрес** — «номер телефона» устройства. Бывает **приватный** (10.x.x.x, локальный, в интернете
  не маршрутизируется) и **публичный** (виден всему интернету).
- **Порт** — «номер квартиры» внутри IP; одно устройство = много сервисов на разных портах (wg=51820).
- **VPN** — зашифрованный **туннель**: твой трафик едет внутри шифра до нашего сервера, оттуда
  выходит в интернет под **нашим** IP. Сайт видит наш IP (не твой); твой провайдер видит шифр
  (не содержимое).
- **Пара ключей** (асимметричная криптография): **приватный** (секрет, никому) + **публичный**
  (можно раздавать). Они математически связаны. Приватным «доказываешь, что это ты»; публичным
  тебе шифруют/проверяют. Знать публичный ≠ вычислить приватный.
- **Симметричный ключ** — один общий секрет для шифрования (быстро). Туннель шифруется именно им,
  а пара ключей нужна, чтобы этот общий секрет безопасно «договорить».

### Глоссарий аббревиатур (быстрый возврат)
- **NAT** — подмена адреса отправителя на публичный, чтобы приватный IP вышел в интернет.
- **exit-IP** — публичный IP ноды, под которым выходят все юзеры (снаружи — один адрес).
- **DPI** — «глубокий анализ пакетов» провайдером/цензором (как ловят и режут VPN).
- **FDE** — full-disk encryption (шифрование всего диска, LUKS).
- **tmpfs** — «диск» в оперативке (исчезает при выключении).
- **mTLS** — взаимный TLS: обе стороны предъявляют сертификаты.
- **HMAC** — отпечаток данных с секретом (нельзя подделать без секрета).
- **FSM** — конечный автомат (набор разрешённых состояний и переходов; у нас — счёт).
- **IPAM** — учёт/выдача IP-адресов.
- **cloud-init** — скрипт «первого запуска» облачного сервера.

### Шпаргалка продавца: фраза клиенту ↔ что под капотом
| Фича | Клиенту (1 фраза) | Под капотом |
|---|---|---|
| No-KYC | «Без имени, почты, телефона — только номер» | account-number 66 бит, в БД только HMAC |
| Браузерный keygen | «Твой ключ создаётся в браузере, мы его не видим» | X25519 в JS, на сервер только pubkey |
| No-logs | «Не пишем кто / куда / когда» | ноды RAM-only, CP без client-IP, проверка в CI |
| DNS | «Свой DNS, запросы не пишем» | unbound по-нодно, `log-queries no` |
| RAM-only | «Серверы без диска — изымать нечего» | tmpfs + no-swap + FDE |
| Крипта | «Monero/BTC/Lightning, без карт» | non-custodial, скраб платёж↔аккаунт |
| .onion | «Доступ через Tor без раскрытия IP» | Tor hidden service |
| Kill-switch | «Отвалился VPN — нет утечки» | клиент + null-route IPv6 на ноде |

# Часть 1. Что мы ПРОДАЁМ (клиент-facing обещания)

## 1. WireGuard — фундамент (как вообще устроен туннель)

**Что это.** Современный VPN-протокол, живёт прямо в ядре Linux (быстрый, маленький, аудируемый).

**Как работает.**
1. У клиента и у сервера — своя пара ключей (curve25519). Они заранее знают **публичные** ключи
   друг друга (мы кладём их в конфиг).
2. **Хендшейк** (протокол Noise): за пару пакетов стороны договариваются об общем **симметричном**
   сеансовом ключе (шифр ChaCha20-Poly1305). Дальше весь трафик шифруется им. Ключ перевыпускается
   каждые ~2 минуты — это «forward secrecy» (украв один, не расшифруешь прошлое).
3. Всё едет поверх **UDP** на один порт (у нас 51820 и 443). Твой обычный пакет шифруется,
   заворачивается в UDP и летит на `Endpoint` сервера.
4. **AllowedIPs** = «какие адреса принадлежат этому peer'у». У клиента `0.0.0.0/0, ::/0` означает
   «весь мой трафик — в туннель». На сервере для тебя — только твой адрес `/32`.
5. **wg0** — виртуальная сетевая карта. ОС маршрутизирует пакеты в неё, WireGuard их шифрует и шлёт.

**У нас.** Клиент — **официальный** WireGuard (своего приложения нет). Сервер (нода) — ядро Linux +
команды `wg`, которые отдаёт наш агент. Конфиг собирается без приватника (см. п.3).

**Подвох.** «Ванильный» WG узнаётся DPI по сигнатуре хендшейка → его режут в RU/IR/CN. Обфускация
(маскировка под обычный трафик) требует НЕ-официального клиента → у нас post-MVP, в гайдах честно.

## 2. No-KYC аккаунт (account-number)

**Что обещаем.** Вход без имени/почты/телефона — только 20-значный номер (как у Mullvad).

**Как работает.**
- При первой оплате генерим 20 случайных цифр ≈ **66 бит энтропии** (10^20 вариантов — перебрать
  нереально).
- На сервере храним **не сам номер**, а его «отпечаток» = `HMAC-SHA256(pepper, номер)`. Это
  односторонняя функция: из отпечатка номер не восстановить. `pepper` — секрет в env, не в БД.
- Вход: ты вводишь номер → сервер считает тот же отпечаток → ищет в БД совпадение.
- Зачем отпечаток: украдут БД — там только хэши, и **без pepper** их даже перебором не проверить.
- **Восстановления нет**: мы физически не знаем твой номер (только отпечаток). Потерял = всё.

**У нас.** `control-plane/app/services/account_number.py`. На входе — защита от перебора (п.16).

## 3. Браузерный keygen — приватник НЕ уходит на сервер (наша killer-фича честности)

**Что обещаем.** Ключ от твоего туннеля рождается у тебя в браузере; сервер его никогда не видит.

**Как работает.**
- WireGuard-ключ = пара curve25519. Приватный — 32 случайных байта; публичный — производный.
- JS в браузере берёт 32 байта из `crypto.getRandomValues` (приватный) и считает публичный =
  `X25519(приватный, 9)`. Это чистая математика на устройстве.
- На сервер уходит **только публичный** ключ. Сервер отдаёт «полконфига» (свой pubkey, endpoint,
  твой выданный IP, DNS, MTU, AllowedIPs) — **БЕЗ** строки `PrivateKey`.
- Браузер локально подставляет приватник, рендерит `.conf` и QR. Приватник в сеть не уходит вообще.
- **Fallback** без JS / Tor «Safest»: ты сам делаешь `wg genkey | wg pubkey` и вставляешь только pubkey.

**У нас.** `web/static/wg-keys.js` (наш X25519 проверен тест-вектором **RFC 7748** в CI),
`config_builder.py` рендерит конфиг с плейсхолдером вместо приватника → сервер технически не может
его отдать.

**Почему важно.** Именно это делает «мы не видим твой ключ» **проверяемым** (открой wg-keys.js и
убедись), а не голословным.

## 4. No-logs (не пишем трафик / сессии / DNS)

**Что обещаем.** Мы не храним, кто, когда и куда ходил.

**Как работает (где это обычно логируется — и как мы НЕ).**
- Обычный VPN пишет: IP клиента, время подключения, объём трафика, DNS-запросы. Это и есть «логи».
- У нас **нода** обрабатывает пакеты в RAM и НИЧЕГО из этого не пишет на диск. На control plane
  уходят только **агрегаты по ноде** (cpu/ram/число peer'ов), не пер-юзер.
- В БД CP лежит только: отпечаток номера, статус подписки, pubkey устройства + выданный IP. Нет
  client-IP, нет таймстемпов хендшейка, нет трафика по юзеру.
- Reverse-proxy перед кабинетом настроен **без client-IP** в логах (проверяется в CI).

**У нас.** `docs/no-logs-inventory.md` (таблица: что/где/RAM-vs-диск/срок/чистка),
`app/logging/no_pii_filter.py`, `scripts/check_no_pii_logs.sh`.

**Честность.** Open-source кода ≠ доказательство, что на сервере крутится он же. Поэтому паровозом:
warrant canary + RAM-only + внешний аудит.

## 5. DNS без логов и по-нодно + защита от утечек

**Ликбез.** DNS — «телефонный справочник» интернета: переводит `site.com` → IP. Обычно это делает
резолвер провайдера, и он **видит все домены**, которые ты открываешь.

**Что обещаем.** DNS-запросы идут через **наш** резолвер, который их не логирует, и он стоит на
**каждой ноде отдельно**.

**Как работает.**
- В конфиг прописан `DNS = <IP резолвера ноды>`. Клиент шлёт DNS-запросы внутрь туннеля, к нему.
- Резолвер (unbound) на ноде: `log-queries: no`, RAM-only, резолвит сам от корневых серверов.
- **По-нодно** (а не один центральный) → нет единой точки, где видны DNS всех юзеров сразу.
- **Защита от утечки**: «утечка DNS» — когда запрос идёт мимо туннеля, к провайдеру. Полный
  AllowedIPs + DNS в конфиге это закрывают. **IPv6-утечка**: если у ноды нет IPv6 — мы заворачиваем
  `::/0` в туннель и **дропаем** на ноде, чтобы v6 не утёк напрямую.

**У нас.** `infra/dns/unbound-nolog.conf`, IPv6 null-route в `config_builder.py` и `agent/nft.py`.

## 6. RAM-only ноды (diskless)

**Что обещаем.** Серверы не пишут на диск ничего, что можно изъять.

**Как работает.**
- Сервер грузит ОС и держит рабочие данные (wg-конфиги, счётчики) в **оперативке** (tmpfs). RAM
  стирается при выключении — забрать нечего.
- **No-swap**: своп — это «слив» RAM на диск при нехватке памяти; отключаем, чтобы данные не утекли
  на диск окольным путём.
- **FDE** (LUKS) на системном диске: даже сама ОС на диске зашифрована.
- Логи journald → **volatile** (в RAM). Приватный ключ ноды — в `/dev/shm` (tmpfs); на reboot
  генерится заново и нода перерегистрируется.
- Итог: при выключении/изъятии ноды RAM пуста, диск зашифрован, логов нет.

**У нас.** `infra/provision-node.sh` (swapoff, journald volatile), `agent/bootstrap.py` (ключ в RAM).

## 7. Анонимная оплата криптой

**Что обещаем.** Платишь Monero / BTC / Lightning / LTC / USDT — без карты и без имени.

**Как работает (по типам).**
- **Monero (XMR)** — приватная *по дизайну* (суммы и адреса скрыты в блокчейне). Наш дефолт. Держим
  свой кошелёк (`monero-wallet-rpc`), на каждый счёт — свежий субадрес.
- **Bitcoin on-chain** — публичный блокчейн (трассируется). Нужно ждать **подтверждений**: транзакция
  попадает в блок (~10 мин), и каждый следующий блок = +1 подтверждение (надёжность).
- **Lightning** — «второй слой» поверх BTC: платёж через каналы, **мгновенный** и дешёвый → это наш
  «быстрый путь» (доступ за секунды).
- **Жизненный цикл счёта (FSM)**: `created → awaiting_confirmation → paid` (или `underpaid/overpaid/
  expired/late_payment`). On-chain выдаём доступ после N подтверждений (конфиг); Lightning — сразу.
- **Non-custodial**: средства идут на **наши** кошельки, мы не держим клиентские балансы.
- **Связь платёж↔аккаунт скрабится** после активации → крипто-трейс не ведёт к личности.

**У нас.** `app/payments/` (monero/btcpay/gateway), `services/billing_fsm.py`, `services/purchase.py`.

**Подвох.** USDT прозрачен и Tether может заморозить адрес → помечен как менее приватный, off-switch.

## 8. .onion (Tor) доступ к кабинету

**Ликбез.** Tor прячет твой IP, прогоняя трафик через 3 случайных узла. `.onion` — сайт, доступный
только внутри Tor (без обычного домена, DNS и центров сертификации).

**Что обещаем.** Кабинет доступен по .onion — обходит Cloudflare/блокировки, не раскрывая IP.

**Как работает.**
- На сервере — Tor с «hidden service»: он генерит .onion-адрес (производный от ключа сервиса) и
  пробрасывает входящие соединения на наш кабинет.
- Клиент в Tor Browser идёт по .onion → трафик не выходит в обычный интернет, нет DNS-резолва, нет CA.
- Кабинет server-rendered и работает **без обязательного JS** → совместим с Tor «Safest».

**У нас.** `infra/tor/torrc`.

## 9. Kill-switch / защита от утечек (на стороне клиента)

**Что указываем (в гайдах).** Если VPN отвалился — трафик не утекает напрямую.

**Как работает.**
- Это функция **официального клиента/ОС**, не наша серверная. Полный AllowedIPs (`0.0.0.0/0, ::/0`)
  + опция «block untunneled traffic» → при разрыве пакеты блокируются, а не идут голыми.
- IPv6-лик закрываем заворачиванием `::/0` в туннель + дроп на ноде (если у ноды нет v6).

**У нас.** Гайды `web/static/guides/*`, null-route в `agent/nft.py` и `config_builder.py`.

## 10. Abuse — только на уровне exit-IP (прямое следствие no-logs)

**Ликбез.** **exit-IP** — публичный IP ноды, под которым весь трафик юзеров выходит в интернет
(через NAT, см. п.15). Снаружи все юзеры ноды выглядят как **один** IP.

**Суть.** При честном no-logs мы **не можем** сказать «этот abuse сделал юзер X» — связи
«exit-IP + время → юзер» у нас нет. Поэтому меры только на уровне ноды/exit-IP: блок портов,
null-route, ротация IP, отключение P2P. Ретро-деанона нет — это **дизайн**, а не недоработка.

**У нас.** AUP `docs/legal/aup.md`; действия применяет агент на ноде.

# Часть 2. Бэкенд / инфра — как это всё держится

## 11. Control plane — «источник правды»

Центральный сервис (FastAPI) + БД (PostgreSQL). Знает всё: аккаунты, подписки, ноды, peer'ы, IP,
инвойсы. Кабинет, .onion, админка и агенты ходят только в его API — никакой логики «на стороне».
Это **главная мишень** → отделён от нод, за reverse-proxy без client-IP + Tor, БД шифруется
at-rest, бэкап шифрованный оффсайт. Файлы: `control-plane/app/`.

## 12. IPAM (выдача IP-адресов)

**Ликбез.** Каждому устройству в туннеле нужен уникальный IP из подсети ноды (напр. `10.7.0.0/24` =
адреса `.1….254`). `.1` — сам сервер.
- Добавили устройство → IPAM выдаёт наименьший свободный (`.2`, `.3`, …).
- Удалили → адрес освобождается и переиспользуется. Строку аренды **удаляем целиком** → нет истории
  «этот аккаунт держал IP X» (для no-logs).
- Кончились адреса → ошибка, нужна новая подсеть/нода. Файлы: `services/ipam.py`.

## 13. Node-агент + mTLS / подписи (CP ↔ нода)

На каждой ноде — мини-сервис (агент). CP командует ему «добавь/сними peer» по HTTP.
Защита канала: **mTLS** (обе стороны предъявляют сертификаты — взаимная аутентификация) +
**HMAC-подпись** тела запроса секретом ноды (защита от подделки/повтора). Агент применяет команды
через `wg set` и отдаёт **агрегатный** health. Файлы: `node-agent/agent/`, `app/security/signing.py`,
`services/node_client.py`.

## 14. API-провижининг RAM-only нод (твой вопрос — подробно)

Это про то, как поднять новую ноду **автоматически, скриптом, без ручных кликов в панели хостера.**

**Шаги.**
1. **Заказ сервера через API хостера.** У крипто-хостеров (напр. **SporeStack**) есть REST-API/CLI:
   «дай VPS, вот оплата в BTC/XMR» → в ответ IP нового сервера и доступ. Никакой ручной регистрации
   и KYC.
2. **cloud-init.** При первом включении облачный сервер читает «скрипт первого запуска» (cloud-init);
   мы передаём ему наш `infra/cloud-init/node.yaml`. Он:
   - выключает swap, ставит wireguard/nftables/unbound;
   - включает `ip_forward` (разрешает ядру пересылать чужие пакеты — без этого NAT не работает);
   - переводит journald в RAM, ставит unbound без логов;
   - запускает `provision-node.sh` и наш агент.
3. **Авто-регистрация.** Агент при старте:
   - генерит wg-ключ ноды в RAM;
   - идёт в CP `POST /v1/nodes/register` с **одноразовым токеном** (его мы заранее создали в админке
     и положили в cloud-init);
   - CP проверяет токен и отдаёт ноде её сеть (подсеть, server-IP, DNS) + `agent_secret`;
   - нода поднимает интерфейс `wg0`, ставит nftables-NAT, начинает слать health.
4. **Готово.** Нода появляется в админке как `active` и попадает «в продажу» как локация — без ручных
   действий, повторяемо.

**Зачем именно «RAM-only + API».** Ноды становятся «скотом, а не питомцами» (cattle, not pets):
упала / изъята / заблокирована хостером → поднял новую за минуты, а на старой **забрать нечего**
(RAM пуста, диск шифрован, логов нет). Это и масштабирование, и устойчивость к изъятию.

**У нас.** `infra/cloud-init/node.yaml`, `infra/provision-node.sh`, `agent/registration.py` +
`agent/bootstrap.py`, `app/api/nodes.py`, `services/node_registration.py`.

## 15. NAT / nftables / forwarding (как трафик выходит в интернет)

**Ликбез.** У клиента приватный IP (`10.7.0.5`) — интернет такие не маршрутизирует. Нужен
**NAT (masquerade)**: нода подменяет адрес отправителя на свой **публичный** (exit-IP), запоминает
соответствие, и обратные ответы раздаёт назад в туннель нужному клиенту.
- `ip_forward=1` — разрешает ядру пересылать пакеты между интерфейсами (`wg0` ↔ `eth0`).
- **nftables** — фаервол/NAT ядра. Наши правила: «трафик из `10.7.0.0/24` на выходе `eth0` →
  masquerade»; форвардинг разрешён; v6 без поддержки → `drop` (анти-лик); проброс `443 → 51820`.
- Поэтому снаружи все юзеры = один exit-IP (см. п.10). Файлы: `node-agent/agent/nft.py`.

## 16. Reverse-proxy без client-IP + защита входа

- Перед кабинетом стоит прокси (Caddy/nginx). Обычно он пишет IP клиента в лог и передаёт его
  приложению (заголовок `X-Forwarded-For`). Мы **отключаем** и то и другое (формат лога без IP,
  заголовки с IP не пробрасываем). Проверяется в CI (`scripts/check_no_pii_logs.sh`).
- **Защита входа** от перебора: эфемерный счётчик попыток в RAM по хэшу IP (сам IP не хранится),
  + одинаковый ответ на «неверный формат» и «не найдено» (анти-энумерация). Файлы:
  `app/security/rate_limit.py`, `infra/reverse-proxy/`.

## 17. Шедулер (крон) — жизненный цикл подписки

Фоновый процесс периодически: проверяет подписки → истекла + grace вышел → снимает все peer'ы
(команда агенту) → доступ закрыт; шлёт opt-in email-напоминания за 3 и 1 день; скрабит старые связи
инвойс↔аккаунт; снимает упавшую ноду с продажи. Файлы: `app/scheduler/`.

## 18. Крипто-примитивы (что и зачем)

- **HMAC** — «отпечаток с секретом»: account-number, подписи запросов агенту.
- **Fernet** (AES) — симметричное шифрование: опциональный email, TOTP-секрет.
- **scrypt** — намеренно медленный хэш пароля админа (стоек к перебору).
- **TOTP** — 6-значные коды 2FA (как Google Authenticator): считаются из секрета + текущего времени.
- **Reed-Solomon** — коды коррекции ошибок в QR (читается, даже если частично закрыт/смазан).
- **age** — шифрование бэкапов CP публичным ключом (приватный — оффлайн, не на сервере).
- Файлы: `app/security/`, `infra/backups/`.

## Путь одного пакета (всё вместе, по шагам)

Ты открываешь `site.com` в браузере, VPN включён:

0. **DNS сначала.** Браузеру нужен IP для `site.com`. Запрос идёт **в туннель** к резолверу ноды
   (не к провайдеру). Провайдер не видит, какой домен ты спросил.
1. **Браузер делает пакет:** от `10.7.0.5` (твой туннельный IP) к IP сайта.
2. **ОС смотрит маршрут:** адрес попадает в `AllowedIPs = 0.0.0.0/0` → пакет уходит в интерфейс `wg0`.
3. **WireGuard шифрует** пакет сеансовым ключом, заворачивает в **UDP** и шлёт с твоего реального IP
   на `Endpoint` ноды (`:51820` или `:443`).
4. **Провайдер видит** только UDP-шифр между тобой и нодой — ни содержимого, ни `site.com`.
5. **Нода (`wg0`) расшифровывает** → получает исходный пакет от `10.7.0.5`.
6. **`ip_forward` + nftables masquerade:** нода меняет отправителя `10.7.0.5` → свой публичный
   **exit-IP**, запоминает соответствие и шлёт пакет в интернет.
7. **Сайт видит** запрос от **exit-IP** ноды (не от тебя) и отвечает на него.
8. **Обратно:** по таблице NAT нода понимает, что ответ — твой → шифрует и шлёт назад в туннель → браузер.

**Кто что видит:** провайдер → шифр; сайт → exit-IP ноды; нода → твой трафик *в моменте, в RAM*
(не пишет); мы в БД → **ничего** из этого. Вот почему «отдавать нечего» — это не лозунг, а следствие
маршрута.
