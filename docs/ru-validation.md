# Валидация RU-транспорта (VLESS+Reality) до продажи

Как довести Reality-ноду от «поднята» до «доказано работает из РФ». Порядок жёсткий:
**сначала тест, потом гайд, потом продажа.** Пока не пройден живой РФ-тест (§4) —
`available_for_sale=false`, транспорт **не продаём** (roadmap-гейт).

Постановка ноды — в [`deploy.md §6.2`](deploy.md). Здесь — что делать ПОСЛЕ того, как нода
`active` в админке: выдать себе доступ, прогнать проверки, снять гейт.

```
[1] нода active ──▶ [2] грант себе ──▶ [3a] смок через РФ-SOCKS5 ──▶ [4] живой РФ-тестер ──▶ [5] продажа
   (deploy §6.2)      (grant_time)      [3b] инфра-достижимость          🔴 ГЕЙТ            available_for_sale
```

## Что может сделать оператор, а что — нет (важно)

Живого клиента в РФ у нас нет, оператор не в РФ. Отсюда — **три уровня уверенности**, от
слабого к сильному. Ни один нижний не заменяет верхний:

| Проверка | Что доказывает | Чего НЕ доказывает |
|---|---|---|
| **check-host / RIPE Atlas** (§3b) | IP/ASN не в блоклисте, :443 достижим | ничего про DPI-поведение ТСПУ |
| **смок через РФ-SOCKS5** (§3a) | Reality-хендшейк проходит по РФ-пути | стабильность у реального юзера (у прокси свой хоп/обрывы/гео) |
| **живой РФ-тестер** (§4) | транспорт реально живёт под ТСПУ | — (это и есть истина) |

**FALSE-NEGATIVE честно:** провал смока через прокси неоднозначен — режет ТСПУ или лёг сам
прокси? Смотри клиентские логи. **PASS обнадёживает, но не гарантирует.** Поэтому продажу
открывает только §4.

> ✅ **Уровень 0 (фундамент) — протокол-интероп ПОДТВЕРЖДЁН (2026-07-13).** Прогнан реальный
> локальный хендшейк VLESS+Reality+XHTTP на пиннутом xray v26.3.27: серверный конфиг
> (`node-agent/agent/xray.render_config`) + клиентский из `vless://`-ссылки (`vless_link`)
> поднимаются, `xray -test` обоих зелёный, живой трафик идёт **в обе стороны** (приём + полная
> отдача 128КБ — путь Telegram/звонков). Значит **сам транспорт/конфиги работают** — если из
> РФ (§3a/§4) не пойдёт, причина в IP/ASN площадки, а не в нашем коде. Воспроизвести: поставить
> xray-core локально, отрендерить оба конфига, прогнать curl через клиентский socks.

## 1. Нода `active`

См. [`deploy.md §6.2.1`](deploy.md) (turnkey) — оператор поднимает `vless_reality`-ноду на
своём VPS вне РФ (абуз-толерантном, TCP 443 открыт), нода сама ставит Xray и регистрируется в CP.
Диагностика на ноде (`systemctl status xray`, `ss -ltnp | grep :443`, `nft … 443`) — там же.
`available_for_sale` на этом этапе **оставь выключенным** (тест-нода).

## 2. Выдать себе доступ без крипты

Метод «оператор-грант» — время начисляется напрямую, без платёжного инвойса. **На хосте
control-plane** (там же БД):

```bash
docker compose exec control-plane python scripts/grant_time.py --new --days 30
#  → ACCOUNT_NUMBER=XXXX-XXXX-XXXX-XXXX  (печатается ОДИН раз — сохрани)
#     EXPIRES_AT=...
```

Затем в браузере: `/login` этим номером → **Устройства → Добавить** → выбери Reality-ноду
(если `available_for_sale=false`, временно включи её в админке ИЛИ добавь устройство до
снятия с продажи) → получишь **`vless://…#privacyvpn <город>`** и QR (base64-подписку).

> Тест-ноду не обязательно светить в продаже, чтобы привязать устройство: можно на минуту
> включить `available_for_sale`, добавить устройство, выключить обратно. Привязанный пир
> остаётся.

Скопируй `vless://`-ссылку — она вход для §3a и §4.

## 3a. Смок через РФ-SOCKS5 (поведенческая проба «как из РФ»)

Единственный способ прогнать хендшейк через ТСПУ без человека в РФ — завернуть **клиентский
dial** в **резидентский/мобильный** РФ-SOCKS5. Скрипт [`control-plane/scripts/ru_smoke.py`](../control-plane/scripts/ru_smoke.py)
строит Xray-клиент с цепочкой `vless-reality → dialerProxy → socks5(РФ) → нода:443`.

```bash
# структурный self-test сборщика (без сети, без xray) — можно прямо сейчас:
python control-plane/scripts/ru_smoke.py --selftest

# боевой прогон (нужен бинарь xray в PATH + РФ-SOCKS5):
python control-plane/scripts/ru_smoke.py \
    --link 'vless://…#nl-1' \
    --ru-socks socks5://user:pass@RU_HOST:1080 \
    --expect-ip <WAN-IP-ноды> \
    --minutes 8
```

Скрипт: `xray -test` (валидирует конфиг) → поднимает клиент → сверяет внешний IP
(`--expect-ip` = WAN ноды) → **проверяет ОТДАЧУ** (POST 512KB — тот самый трафик, что нужен
Telegram/звонкам/выгрузке; `--upload-kb`, 0=выкл) → крутит стабильность 8 мин, тик 15 c → отчёт
(uptime %, первый обрыв, отдача OK/ВИСНЕТ). `--config-only` печатает конфиг для ручного запуска.

> Отдача — критична: XHTTP-баг ломает именно её (приём идёт, upload встаёт). Здесь клиент —
> xray-core, где `mode=auto` резолвится корректно, поэтому провал отдачи тут = проблема
> **сервера/транспорта/канала** (а не клиента), и продавать нельзя. На реальных клиентах то же
> самое ломает **Hiddify** (см. §4) — поэтому ведём людей на v2rayNG.

**Требования к прокси (иначе результат — мусор):**
- **ТОЛЬКО резидентский/мобильный РФ-IP.** Датацентр-прокси врёт: у ТСПУ иная политика к
  ДЦ-подсетям, «pass» на нём ничего не значит.
- VLESS(+XHTTP) — TCP, его несёт SOCKS5 CONNECT. **AmneziaWG — UDP**, через SOCKS5 **не
  тестируется**; скрипт vless-only, awg-ссылку отклонит. AmneziaWG проверяется только §4.

**Читай результат честно:** PASS = «обнадёживает, хендшейк по РФ-пути проходит», НЕ «продаём».
FAIL = смотри логи (`*.log` рядом с конфигом): reject хендшейка ≈ ТСПУ; connection refused к
прокси ≈ прокси лёг. Один прокси лёг — возьми другой, прежде чем винить транспорт.

## 3b. Инфра-достижимость (параллельно, дёшево)

Ловит только блок по IP/ASN и «порт закрыт» — не DPI. [`infra/ru-validation/ru_reach.py`](../infra/ru-validation/ru_reach.py):

```bash
python infra/ru-validation/ru_reach.py <WAN-IP-ноды> --port 443
#  check-host.net TCP-connect с РФ-узлов → OK/БЛОК по каждому + вердикт.
#  Внизу — готовые команды RIPE Atlas (точнее, но нужен аккаунт+кредиты).
```

Все РФ-узлы зелёные → IP/ASN чист, 443 открыт. Красные только из РФ (зелёные из других стран)
→ режут по IP/подсети/ASN → **меняй хостинг/ASN**, транспорт ни при чём.

## 4. 🔴 Гейт: живой РФ-тестер

Инфра-достижимость и смок-через-прокси ≠ выживаемость под ТСПУ у реального юзера. Дай тестеру
`vless://`-ссылку/QR и страничку [`ru-beta-tester.md`](ru-beta-tester.md): коннект, exit-IP,
**ОТДАЧА/upload**, стабильность 5–10 мин, логи при отказе. **Пока не пройдено —
`available_for_sale` не трогаем, RU-гайд не публикуем, транспорт не продаём.**

> ⚠️ **Клиент решает.** Транспорт — VLESS+Reality+**XHTTP**; его надёжно тянет только движок
> **Xray** (v2rayNG, v2rayTun, Streisand, десктопный xray-core). **Hiddify по умолчанию гонит
> XHTTP через свой sing-box-форк, где `mode=auto` не резолвится → отдача (upload/звонки) висит**
> (hiddify-app#2082): приём есть, выгрузка стоит. Параметр `mode` из ссылки Hiddify при импорте
> теряет — «починить ссылкой» нельзя. Поэтому тестер и гайд идут на **v2rayNG**, а тест-скрипт
> `ru_smoke.py` использует бинарь xray-core (там `mode=auto` корректно резолвится в `stream-one`).
> **Обязательно проверь upload у живого тестера** — быстрый чек «сайт + IP» этот баг НЕ ловит.
>
> Опциональное усиление (НЕ обязательное, НЕ чинит Hiddify): выставить `mode=stream-one` явно в
> `xray.py` (сервер) И `vless_link.py` (ссылка) — behavior-identical для xray-core, но требует
> согласованного деплоя обеих сторон и повторного `xray -test`. Не делали: `mode=auto` на пине
> v26.3.27 подтверждён корректным, а Hiddify параметр всё равно игнорирует.

Если рвётся у живого тестера — почти всегда **хостинг/ASN** (ТСПУ душит по объёму+географии),
а не сам Reality: пробуй другую площадку/ASN, отсканируй non-CDN `dest` в подсети своей ноды
(`RealiTLScanner`, см. `deploy.md §6.1`), `fp=firefox` (уже дефолт). Смена только SNI/порта
обычно не помогает.

## 5. После прохождения гейта → продуктизация

Только когда §4 пройден:
1. `available_for_sale=true` на Reality-ноде в админке.
2. Опубликовать RU-гайд (`web/templates/guides/ru-vless.html` — уже готов, ждёт снятия гейта;
   добавить в индекс `/guides` и топбар/дисклеймер) — см. отдельный чек-лист в гайде.
3. Упаковка/цена RU-плана — отдельное решение (см. `docs/roadmap.md`).

### Приложение: почему нельзя было «просто подключиться и проверить»

- Оператор вне РФ → его подключение проходит НЕ через ТСПУ → ничего не проверяет.
- Реальный РФ-клиент — только человек с устройством в РФ (§4) ИЛИ прокси с РФ-IP (§3a,
  слабее). Датацентр-прокси в РФ ≠ пользовательская сеть — обманчив.
- Инфра-пробы (§3b) видят IP/ASN/порт, но слепы к поведенческому DPI.
